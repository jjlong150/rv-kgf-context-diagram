SCHEMA — READ THIS FIRST:
The file has a top-level `styles` dictionary that is the authoritative schema for
each style. Every node and edge carries a `style` key; resolve it against `styles`
to get that style's `type` ("node"/"edge"/"cluster"), `description`, and
`properties`. Style properties describe what is inherently true of every node or
edge of that type — never a specific instance. Use whatever keys actually appear;
the vocabulary below explains the ones you are most likely to see.

STYLE PROPERTY VOCABULARY:
  Nodes
  - kind: actor | app | datastore | annotation. subtype refines it (e.g. homegrown,
    cloud, queue, person).
  - Apps: code_ownership (internal | vendor | community | partner | mixed),
    operated_by (internal | vendor | partner), support_model (who supports it).
  - Data stores: structure, persistence, access_pattern, concurrency_model.
  - Actors: actor_role (human | automated | system).
  Edges
  - status — governance of the connection PATTERN, not of this specific
    integration:
      approved          no objections
      requires_approval permitted only with an explicit approval or exception
      under_review      architecture position not yet decided
      deprecated        permitted for existing use; migrate away
      prohibited        not permitted
  - preferred_alternative — the name of another style that should be used
    instead. That style is usually NOT in `styles`, because only styles in use are
    exported. Its absence is expected, not an export error. Interpret the
    alternative from its self-describing name (e.g. file_transfer_sftp = SFTP via
    file transfer) and from the governance note at the end of the current style's
    description (e.g. "Approved; SFTP preferred.").
  - risk_level (low | medium | high) — inherent risk of the pattern.
  - modernity (modern | established | legacy) — age of the technology.
  - via — the integration path or intermediary (api_gateway, esb, forward_proxy,
    reverse_proxy, direct_network, message_broker, email, file_transfer, telephony).
  - protocol_type; transport (network layer only: tcp, udp, tcp_udp, ssh,
    file_io, circuit); directionality (request_response | push | pull |
    push_pull | bidirectional).
  - encryption_in_transit:
      enforced        the protocol always encrypts
      optional        depends on configuration (e.g. STARTTLS, LDAPS, TLS
                      listeners)
      none            cleartext by design
      not_applicable  local file I/O
  - reliable_delivery, ordered_delivery, real_time, synchronous — protocol
    characteristics.
  - Data store edges: interaction_type (gets | sends) says which side initiates;
    operation (read | write | delete | execute | consume) says what happens to the
    data. They can differ (e.g. sends_to_sql_select is a read).
  - Actor-to-application edges carry no status or risk_level. Their color
    identifies the actor type, not governance, so infer nothing about approval
    from their absence.
  Authentication is deliberately NOT a style property. It comes only from
  instance-level data (e.g. auth_mechanism). Where that is missing, treat
  authentication as unknown.

INSTANCE-LEVEL PROPERTIES:
An individual node or edge object may carry its OWN `properties` field (a sibling
of `style`/`label`/etc.), holding per-instance facts from the source workbook. Per
the published schema, this field is entirely omitted (not an empty object) whenever
the source data was blank, so check for its presence. Its key names are chosen by
the author. Expect keys such as data_classification, contains_pii, auth_mechanism,
retry_strategy, failure_disposition, failure_alerting, approximate_volume,
agreements_in_place, stability, criticality, hosting_model, regulatory_scope,
end_of_support_date, redundancy_model, deployment_model, data_residency,
retention_period, encryption_at_rest, backup_strategy, origin, population_scale,
channel.
contains_pii, encryption_at_rest and agreements_in_place are booleans
(true/false); other instance values are display text as entered in the workbook
(e.g. "Dead Letter Queue").
The three failure keys are independent:
  - retry_strategy: how the caller retries.
  - failure_disposition: what happens once retries are exhausted. "Unhandled"
    means known to be missing; an absent key means unknown.
  - failure_alerting: whether operations is notified.
On edges these keys describe how the application handles failure. On data
stores they are expected only for queues, where they describe the broker's
redelivery, dead-letter and monitoring behavior.

INSTANCE VS. STYLE PRECEDENCE:
Style and instance keys are designed to be mostly disjoint:
  - Style properties describe the type.
  - Instance properties describe the specific integration or component.
Apply these rules:
  - Same key at both levels (e.g. encryption_in_transit): the instance value
    overrides the style default for that node/edge. Say so explicitly ("X overrides
    the style default of Y").
  - Instance key with no style-level counterpart: an additional fact, not an
    override.
  - Related but different keys: do not treat as overrides or conflicts.
    - Instance `stability` (e.g. Deprecated) is the lifecycle of this integration.
      Style `status` (e.g. approved) is the governance of the pattern. Report both.
    - Instance `approximate_volume` is not a counterpart to any style key.
  - Values may differ in format between levels ("On Premise" vs "on_prem"). Compare
    them by meaning, not by string.
  - No `properties` field at all: everything about that node/edge comes from its
    style. Say so, and don't present a style-level default as a verified fact about
    that instance.

Ignore `debuglabel` fields entirely (diagnostic-only, not architectural content). If
any node has `defined: false`, note it separately as a tool-synthesized artifact
rather than an author-modeled component (it will never carry `properties`).

TRUST BOUNDARIES:
Reconstruct the nesting of `cluster` fields into a zone hierarchy. Each node or
cluster points to a parent cluster id, and clusters can nest inside clusters. For
example, "Corporate Applications" vs "Internet," with inner zones like "Perimeter
Network," "Cloud Service Provider," "Consumer's Home," "Email Services."

For every edge, note whether it crosses zones, and treat zone-crossing edges as
higher scrutiny in the security assessment.
  - Styles do not carry boundary information. Infer boundary-crossing from the
    cluster hierarchy.
  - Use `security_boundary_crossed` only when an instance provides it.
  - A proxy style (via forward_proxy / reverse_proxy) does not by itself mean that
    edge crosses a zone. Often only the next hop does.

NON-UNIQUE IDS:

allowed by the schema (e.g. separate enqueue/dequeue edges between the same app and
queue). Key each relationship by (source, target, style, label). Don't deduplicate
edges that share an id or endpoint pair.
